# EC2 프리티어 기준 실시간 조회자 수 기능 운영 판단

## 현재 전제
- 일일 사용자 수: 약 100명
- 동시 사용자 수: 많아도 수십 명 수준 예상
- 기능 범위: 매물 상세보기를 "지금 보고 있는 인원 수" 표시
- 기준 이벤트: 사용자가 상세보기를 열었을 때만 집계

## 결론
- 현재 트래픽 규모라면 EC2 프리티어에서도 무리 없이 시작할 가능성이 높다.
- 다만 처음부터 `WebSocket + Redis`까지 한 번에 올리는 것은 과하다.
- 현재 조건에서는 아래 순서가 가장 현실적이다.

권장 순서
1. 1단계: REST + presence 등록/해제 + 짧은 주기 폴링
2. 2단계: 사용자가 늘면 SSE 전환
3. 3단계: 동시 접속이 더 늘면 WebSocket + Redis 전환

## 왜 프리티어에서도 가능한가
- DAU 100명은 절대 트래픽이 큰 편이 아니다.
- 동시 수십 명이면 상세보기 실시간 카운트 요청 수도 제한적이다.
- 이 기능은 이미지 스트리밍이나 대용량 계산이 아니라 작은 숫자 상태만 주고받는다.

예를 들어:
- 동시 상세보기 사용자 20명
- 15초마다 폴링

대략적인 요청 수는:
- 초당 약 1.3 요청 수준
- 여기에 상세 입장/이탈 요청이 조금 추가되는 정도

이 정도는 일반적인 소형 EC2에서도 충분히 감당 가능하다.

## 무엇이 부담이 되는가
- 부담의 핵심은 "조회자 수 계산"이 아니라 "실시간 연결 유지 비용"이다.
- REST 폴링은 단순하고 예측 가능하다.
- SSE는 연결을 오래 유지하지만 구현이 비교적 단순하다.
- WebSocket은 가장 유연하지만 연결 관리와 운영 복잡도가 가장 높다.

## 방식별 비교

### 1. REST 폴링

구조
- 상세보기 진입 시 현재 매물에 대해 "입장" 등록
- 상세보기가 열려 있는 동안 10~15초마다 현재 조회자 수 조회
- 상세보기 종료 시 "이탈" 등록
- 서버는 TTL 또는 마지막 활성 시각 기준으로 stale 세션 정리

장점
- 구현이 가장 단순하다.
- EC2 프리티어에서 운영 부담이 가장 적다.
- 기존 REST API 구조에 자연스럽게 붙일 수 있다.
- 디버깅이 쉽다.

단점
- 진짜 실시간은 아니다.
- 카운트 반영이 10~15초 정도 늦을 수 있다.

현재 조건 적합성
- 가장 적합

### 2. SSE

구조
- 상세보기 진입 시 presence 등록
- 서버는 해당 매물 카운트 변화를 SSE로 push
- 상세 종료 시 presence 해제

장점
- 실시간성이 REST 폴링보다 좋다.
- WebSocket보다 단순하다.
- 서버 -> 클라이언트 단방향 알림에는 잘 맞는다.

단점
- 연결 유지 비용이 REST보다 크다.
- 프록시/타임아웃/keep-alive 설정을 신경 써야 한다.
- 입장/이탈은 여전히 REST로 따로 처리하는 경우가 많다.

현재 조건 적합성
- 2단계 전환용으로 적합

### 3. WebSocket + Redis

구조
- 접속 시 매물별 채널 구독
- presence는 Redis Set으로 관리
- heartbeat와 disconnect hook으로 세션 정리
- count 변경 시 즉시 broadcast

장점
- 가장 즉각적이다.
- 규모가 커졌을 때 확장성이 좋다.
- 다양한 실시간 기능으로 확장 가능하다.

단점
- 프리티어 기준으로는 운영 복잡도가 높다.
- 연결 수가 많아지면 메모리 부담이 늘어난다.
- Redis까지 같은 인스턴스에 얹으면 여유가 빨리 줄 수 있다.

현재 조건 적합성
- 지금 당장은 과한 편

## 현재 트래픽 기준 추천안

### 추천 아키텍처
- 프론트:
  - 상세보기 열기 시 presence 등록
  - 상세보기 열려 있는 동안 15초 주기 폴링
  - 상세보기 닫기/페이지 이탈 시 presence 해제
- 백엔드:
  - active viewer presence 저장
  - 현재 viewer count 반환 API 제공
  - stale session TTL 정리

### 왜 이 방식이 맞는가
- 동시 사용자 수가 수십 명이면 15초 폴링으로도 충분히 부하가 낮다.
- 사용자 입장에서 "몇 초 이내 갱신"이면 UX 품질이 충분하다.
- 운영 난이도가 낮아서 장애 가능성이 줄어든다.

## 구체적인 권장 스펙

### 프론트
- 상세보기 진입 시:
  - `POST /listings/{listingId}/viewer-presence`
- 상세보기 열려 있는 동안:
  - 15초마다 `GET /listings/{listingId}/viewer-count`
- 상세보기 종료 시:
  - `DELETE /listings/{listingId}/viewer-presence?viewerSessionId=...`

### 백엔드
- 세션 식별:
  - 브라우저 탭 단위 `viewerSessionId`
- 저장:
  - 처음에는 RDB보다 Redis 권장
  - 다만 아주 단순하게 시작할 경우 인메모리 맵도 가능
- 정리:
  - lastSeen 기반 60~90초 TTL cleanup

## Redis가 꼭 필요한가
- 현재 규모에서는 "반드시" 필요한 것은 아니다.
- 선택 기준은 아래와 같다.

Redis 없이 시작 가능한 경우
- 서버가 단일 EC2 1대
- 재시작 시 실시간 카운트 유실이 문제 아님
- 기능을 빨리 검증하고 싶음

Redis를 바로 쓰는 편이 좋은 경우
- 서버가 2대 이상으로 늘 수 있음
- 앞으로 다른 실시간 기능도 붙일 계획이 있음
- 세션 TTL 정리와 멱등 처리를 더 안정적으로 하고 싶음

현재 조건에서는
- 단일 서버면 인메모리 또는 간단한 저장소로 시작 가능
- 그래도 구현 안정성을 생각하면 Redis가 있으면 더 좋음

## EC2 프리티어에서 주의할 운영 포인트

### 1. 메모리
- WebSocket/SSE는 연결을 오래 잡고 있으므로 메모리 영향을 받는다.
- REST 폴링은 상대적으로 안전하다.

### 2. 타임아웃
- reverse proxy를 쓰면 keep-alive 설정을 확인해야 한다.
- SSE/WebSocket은 idle timeout으로 끊길 수 있다.

### 3. 배포 시 연결 끊김
- 실시간 연결 방식은 배포 순간 연결이 끊길 수 있다.
- 폴링은 이런 문제에 더 둔감하다.

### 4. stale session 정리
- 사용자가 탭을 강제 종료하면 leave 요청이 안 갈 수 있다.
- 서버에서 TTL 정리가 반드시 있어야 한다.

## 간단한 비용/복잡도 판단

REST 폴링
- 비용: 낮음
- 구현 난이도: 낮음
- 운영 난이도: 낮음
- 실시간성: 보통

SSE
- 비용: 중간
- 구현 난이도: 중간
- 운영 난이도: 중간
- 실시간성: 좋음

WebSocket + Redis
- 비용: 중간 이상
- 구현 난이도: 높음
- 운영 난이도: 높음
- 실시간성: 가장 좋음

## 추천 단계별 로드맵

### 1단계: 지금 바로 적용
- REST 폴링으로 구현
- 상세보기 열림 기준 presence 등록
- 15초마다 현재 인원 수 조회
- UI 문구:
  - `지금 3명 보는 중`

### 2단계: 사용자가 늘면 전환
전환 신호 예시
- 동시 상세보기 사용자가 자주 50명 이상
- 폴링 요청이 부담되기 시작
- 더 즉각적인 반영이 필요

이때
- SSE 전환 검토

### 3단계: 더 커지면 확장
전환 신호 예시
- 실시간 기능이 여러 개 필요
- 서버 인스턴스가 2대 이상
- 채팅/알림/상태 공유 같은 실시간 기능 확대

이때
- WebSocket + Redis 전환

## 추천 API 설계

### 1. 입장 등록
`POST /listings/{listingId}/viewer-presence`

request:
```json
{
  "viewerSessionId": "uuid"
}
```

response:
```json
{
  "listingId": 123,
  "viewerCount": 4
}
```

### 2. 현재 인원 수 조회
`GET /listings/{listingId}/viewer-count?viewerSessionId=uuid`

response:
```json
{
  "listingId": 123,
  "viewerCount": 4
}
```

### 3. 이탈 등록
`DELETE /listings/{listingId}/viewer-presence?viewerSessionId=uuid`

response:
```json
{
  "listingId": 123,
  "viewerCount": 3
}
```

## 데이터 정합성 정책
- 같은 `viewerSessionId`가 같은 매물에 중복 입장해도 1명으로 계산
- 같은 세션이 다른 매물로 이동하면 이전 매물에서는 제거
- 로그인 여부와 별개로 탭 단위 세션을 기준으로 계산

## 이 요구사항에 대한 최종 추천
- 현재 조건에서는 EC2 프리티어가 병목이 될 가능성은 낮다.
- 처음부터 실시간 연결 기술을 무겁게 올리기보다, REST 폴링 기반으로 시작하는 것이 가장 안전하다.
- 현재 사용자 수라면 다음 구성이 가장 적절하다.

최종 추천 스택
1. 프론트: 상세보기 기준 15초 폴링
2. 백엔드: presence 등록/해제 API + viewer count API
3. 저장소: 단일 서버면 인메모리로도 시작 가능, 안정성을 원하면 Redis
4. stale session 정리: 60~90초 TTL

## 바로 실행 가능한 의사결정
- 지금 구현은 `REST 폴링 방식`으로 시작한다.
- 문서에 있는 WebSocket/SSE 설계는 이후 확장안으로 유지한다.
- 현재 DAU 100 수준에서는 이 선택이 비용, 복잡도, 운영 안정성 측면에서 가장 균형이 좋다.
